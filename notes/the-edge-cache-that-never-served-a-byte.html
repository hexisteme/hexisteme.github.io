The Edge Cache That Never Served a Byte: Verify Cache Hits by Timing a Warm Call

← hexisteme · notes · 2026-07-18

An endpoint on my serverless backend was supposed to be caching its result at the edge — it said so in the design record, in the code, and in the response headers. The first test that actually timed a warm call showed it re-walking all 29 upstream pages at 2.9 seconds, twice, against a 0.16-second expectation. The cache API is documented as having no effect on the hostname it was deployed to, so every cache that backend ever claimed had never served a byte. Nothing broke, because the spend circuit breakers underneath were quietly absorbing the whole load the cache was credited with removing.

I run a small serverless backend on Cloudflare Workers. One of its endpoints assembles a schedule board by walking 29 pages of an upstream API, then caches the assembled result at the edge. The cache was in the design record, in the code, and in the cache-control header of every response it returned. It had been live in production.

Then a verification step asked it to prove itself. The requirement had been written down in plain words — the second call must come back from the stored value — so it got a test: call the endpoint, call it again, time the second call. The expected number was about 0.16 seconds.

The second call took 2.9 seconds. It had re-walked all 29 upstream pages. I ran it again: 2.9 seconds again. A miss that size, twice, is not a flake.

The cause was in the hostname

The worker was deployed on a *.workers.dev subdomain. Cloudflare's Cache API — caches.default.put() and caches.default.match() — is documented as having no effect there, and the same is true inside the dashboard editor and preview playgrounds. The calls do not fail. put() returns cleanly. match() simply never finds anything.

So the code was right, the deploy was right, and the layer was inert. And not for one endpoint: every cache that backend had ever claimed went through the same API — a per-flight lookup with its own TTL table, a congestion endpoint, a checkpoint endpoint, the schedule board, and a share page whose s-maxage=60 I had been treating as a real 60-second cache. Not one of them had ever served a byte in production.

The shape of that is worth stating on its own, because it is the part that repeats. The defect was not in any of the five call sites. It was in an environment property one level above all of them. Grep the codebase for the cache API and you find five correct usages. Nothing in the code is wrong. Every one of them starts working, unchanged, the day the worker sits behind a custom domain.

Nothing broke, because the layer underneath was paying

Every request that backend had ever served in production ran with zero caching, and that should have produced a signal somewhere. It produced none, and the reason generalizes further than the bug does.

Underneath the cache sat a second protection: per-day spend counters in the SQL store, acting as circuit breakers over the paid upstream. Underneath that, the free-tier quotas of the upstreams themselves. Those two absorbed the entire request volume without complaint. The system looked healthy because it was healthy — just not for the reason the design record gave.

That is the trap in stacked protections. Layer A (the cache) is supposed to remove load. Layer B (the breaker, the quota, the retry budget, the autoscaler) is supposed to bound the damage when load arrives anyway. When A is dead, B covers for it silently, and the only trace is that B's budget is what is actually burning. Absence of failure is evidence about B. It is not evidence about A.

The question that would have caught this in review: if this layer were deleted entirely, what would I observe? If the honest answer is "nothing, for a while," you do not have a monitoring gap — you have an unverifiable claim, and it stays unverifiable until you measure that layer directly. Caches are the common case, but the same silence covers a retry policy that never retries, a rate limiter that is never reached, and a fallback path that is never taken. Any layer whose success signature is identical to a normal response can be missing for months.

A cache you have not timed is an assumption

Here is everything I had accepted as evidence before that timing test:

  • The put() call is in the code, on the right path, with the right key.
  • The response carries cache-control with a sensible TTL.
  • A test asserts the header is present.

None of those observes a hit. The last one is the most seductive, because it is green and it says "cache" in the test name. Reading the cache-control header off a response your own code just built tells you what your code wrote into a header. It says nothing about whether any cache stored the response, and nothing about whether a later request read it back.

Three things actually observe a hit:

  1. Time a warm call. Two identical requests, back to back. Write down the expected number before running it — the point of the expectation is that a miss becomes a failed assertion instead of a shrug at a slow response.
  2. Emit an explicit hit marker. Have the read path set x-cache: HIT or MISS at the point where the lookup returns, not where the response is assembled. Then a hit is directly observable in a curl, in a log line, and in a smoke test.
  3. Count hits and misses. A hit rate is a number you can chart and alert on. A cache with no hit-rate metric is one whose failure mode is silence.

The reason this got caught at all was an accident of wording worth stealing on purpose. The requirement had been stated as behavior ("serve it from the stored value"), not as an optimization. Optimizations do not get assertions; behaviors do. If a cache matters — for cost, for a paid upstream, for a latency budget — write it down as a behavior with a number attached, and it gets a test that is capable of failing.

Why a cache layer quietly runs at a zero percent hit rate

My specific cause was a platform rule about a hostname. The general failure — a cache that is present, correct-looking, and never hit — has a short list of usual suspects. When a warm call comes back cold, walk this before touching the cache code:

CauseThe check that settles it
Environment where caching is a no-op (preview URLs, dev domains, local emulators, dashboard editors)Read the platform docs for the exact hostname and environment you deployed to, not for the product in general
Cache key mismatchLog the key on write and on read, then diff them; query-string order, trailing slashes, and method all move the key
VaryAny Vary on a header that differs per client (User-Agent, Accept-Encoding, Cookie) fragments the entry; Vary: * disables storage outright
Set-Cookie on the responseShared caches generally refuse to store a response that sets a cookie
Cache-Control: no-store, private, no-cache, or max-age=0Print the final response headers; a framework or middleware default may be overwriting what you set
TTL shorter than the gap between requestsCompare the TTL against real inter-request time; a 60-second entry on a page requested every five minutes hits approximately never
Personalization or auth on the pathAuthorization headers and per-user bodies are uncacheable by design; the fix is splitting the cacheable part out, not a longer TTL
Method or status not cacheablePOST responses and many non-200 statuses are not stored by default
LocalityA hit in one node, region, or isolate is a miss in the next; thin traffic spread across many nodes looks exactly like a broken cache
Write path runs, read path does notA feature flag, an early return, or an error branch that skips the lookup gives you a cache that only ever fills

Every row produces the identical symptom — a warm call as slow as a cold one — which is exactly why the measurement comes first and the theory second. I spent no time debugging cache keys, because the timing test told me the layer was inert before I had a chance to guess.

What I replaced it with

The fix was not to make the edge cache work. On that hostname it cannot, and moving the whole deployment behind a custom domain was a larger decision than one endpoint deserved.

Instead the assembled board got a per-isolate in-memory memo, and that became the load-bearing store. Measured on the deployed worker: 1.19 seconds cold, 0.157 seconds warm — close to the number the original test had been expecting all along.

That store is strictly weaker than an edge cache, and it is worth being precise about how. It lives inside one isolate. It dies when that isolate is recycled. A request routed to a different instance pays full price. It is a smaller promise than the one the design record made — but it is a promise I can measure, which the larger one turned out not to be.

The dead caches.default calls stayed in the code on purpose, as dormant scaffolding: they become live and correct the day the worker moves behind a custom domain. That choice has a cost. To any future reader — most often me, three months later — five correct-looking cache calls read as a working cache layer. So the fact went next to the code, in the decision record and in the planning notes, in the form "this layer is inert on this hostname." A phantom layer nobody wrote down gets re-trusted by the next person who greps for it.

Limits

The hostname rule is one platform's documented behavior. The replacement — an in-process memo — only makes sense where a cold miss is survivable and the data is shared across requests rather than per-user. Neither of those transfers automatically.

The claim I would defend is narrower than "your cache is broken." It is that a cache hit is something you can only learn by observing it, and that a stack of protections conceals the death of any single layer for as long as the layer below it has budget.

Two ways this would be shown wrong. If the same worker on a custom domain still re-walked the upstream on a warm call, then the hostname was not the cause and the cache key or Vary was — the measurement would stand, the diagnosis would move. And a near-zero hit rate is not by itself a defect: low traffic, short TTLs, and many nodes can produce one legitimately. The claim is not that zero hits means broken. It is that until you have timed a warm call, you do not know which one you have.

FAQ

Q. Why is my Cloudflare Workers cache not working on workers.dev?
Because the Cache API is documented as having no effect on a workers.dev subdomain, and the same is true in the dashboard editor and preview playgrounds. The calls do not fail: caches.default.put() returns cleanly and caches.default.match() simply never finds anything, so the code looks correct while the layer is inert. The same call sites start working unchanged once the worker is served from a custom domain.

Q. How do I verify that a cache is actually serving hits?
Three things observe a hit. Time a warm call: send two identical requests back to back and write down the expected number before running it, so a miss becomes a failed assertion instead of a shrug at a slow response. Emit an explicit hit marker: set x-cache HIT or MISS at the point where the lookup returns, not where the response is assembled. Count hits and misses, so the hit rate is a number you can chart and alert on. Reading the cache-control header off a response your own code just built verifies none of these.

Q. Why does a dead cache layer cause no visible failure?
Because the layer underneath absorbs what the cache was supposed to remove. In my case per-day spend circuit breakers and upstream free-tier quotas carried the full request volume in production, so the system looked healthy while every cache read missed. Absence of failure is evidence about the layer below, not about the cache. The review question that catches it is: if this layer were deleted entirely, what would I observe? If the answer is nothing for a while, the claim is unverifiable until you measure that layer directly.

Q. What are the most common reasons a cache has a zero percent hit rate?
An environment where caching is a no-op (preview URLs, dev domains, local emulators, dashboard editors); a cache key mismatch between write and read, including query-string order and trailing slashes; a Vary header on something that differs per client; a Set-Cookie on the response, which shared caches generally refuse to store; Cache-Control no-store, private, no-cache or max-age=0 set by a framework default; a TTL shorter than the gap between requests; personalization or Authorization on the path; a method or status that is not cacheable; locality, where a hit in one node is a miss in the next; and a write path that runs while the read path is skipped by a flag or an early return.

Q. Is an in-memory memo a good replacement for an edge cache?
It is a strictly weaker promise, but a measurable one. A per-isolate memo lives inside one instance, dies when that instance is recycled, and gives no benefit to a request routed elsewhere. On my deployed worker it took the endpoint from 1.19 seconds cold to 0.157 seconds warm, which was close to what the original cache test had expected all along. It makes sense where a cold miss is survivable and the data is shared across requests rather than per-user.

Removing a Hidden Effort Prompt Made My Local Qwen 27B Run Valid. It Still Missed the Bar.

← hexisteme · notes · 2026-11-23

A retry of my local Qwen3.8 27B effort experiment sent reasoning_effort: medium as a top-level request field, and the pre-registered overhead check came out at 14 on 10/10 tasks, so the run was valid. It then produced 4/10 applicable patches against a threshold of 5/10 and was rejected; I stopped the 27B experiments on this Mac.

On November 16 an overnight run on my local Qwen3.8 27B finished at 09:12:16. The pre-registration put one check ahead of the score: the prompt overhead, usage.prompt_tokens minus the tokens of the message body, per task. The pre-registration said it had to be about 14 on all 10 tasks. It was 14 on 10/10. The run was valid. The verdict was a rejection: 4/10 applicable patches against a threshold of 5/10.

This is the follow-up to an earlier run that never got a verdict at all. That one tried to remove a reasoning-effort paragraph from the prompt by editing the Ollama Modelfile TEMPLATE. The registered template changed, but the server's prompt did not: the overhead stayed at 52 on 10/10 tasks, the outputs were byte-identical to the baseline, and the pre-registered token check voided the run. This note is about the retry, where the variable finally reached the model, and about why I count a clean rejection as more useful than the void before it.

What the retry changed

Reading the static files, the jinja chat template embedded in the GGUF inserts the paragraph through reasoning_effort|default('xhigh'). With medium there is no paragraph. My guess is that Ollama renders this model's prompt with that embedded template, but I did not confirm which component does the rendering. What the earlier run did show is that the Modelfile TEMPLATE was not the path used for this model, so the lever had to be on the request side.

A daytime probe on November 8 settled which request field worked. I sent the same short message several ways and read the server's prompt_tokens:

requestprompt_tokens
baseline, no effort field61
/v1, top-level reasoning_effort: medium23
/v1, top-level reasoning_effort: low49
chat_template_kwargs with reasoning_effort61

Medium dropped 38 tokens (the 37-token paragraph plus 1 separator). chat_template_kwargs was ignored. The native /api/chat with think behaved like the top-level field.

So the retry was the same experiment as the void run, implemented through the field that worked. Same model, same weights blob, same template and parameters as the baseline, same 10 build-fix tasks, temperature 0.6, top_p 0.95, max_tokens 12,288, seed 0. The one difference was RunConfig.reasoning_effort = "medium", which the harness adds to the config hash and to the request only when it is set, so the baseline's hash did not move. A new hash also meant the run could not read the baseline's generation cache.

The run script repeated the probe right after loading the model and refused to start unless the top-level medium request was effective. On November 16 at 00:34 that probe gave medium 61→23, low 61→49, and chat_template_kwargs ignored, the same as the daytime probe. The run itself went from 03:40:14 to 09:12:16, 5 h 32 m, against 6 h 28 m for the baseline.

Validity first

The pre-registration, written on November 8 before any result, fixed the order: check validity, then judge.

  • Prompt overhead on every task should be ≈ 14 (the baseline's 52 minus 38, ±3). If any task is near 52, the run is void and gets no verdict.
  • As a second signal, report how many outputs are byte-identical to the baseline.

The result was overhead 14 on 10/10 tasks and zero tasks near 52. For the second signal, 0 of the 6 non-empty outputs matched the baseline byte for byte. Four outputs were empty in both runs, 0 characters each, so they are identical by construction, and I did not count them as evidence either way.

In the void run, the byte-identical outputs were independent evidence that the server saw the old prompt; the token overhead was what decided validity. Here the same check points the other way: the outputs changed, which is what should happen when the prompt changes under a fixed seed.

The verdict, in the pre-registered wording

The threshold was the same one my earlier baseline runs used, with no adjustment after the fact: 5/10 or more applicable patches supports the hypothesis, under 5/10 rejects it. "Applicable" means the generated diff got through git apply and reached the tests.

  • Applicable: 4/10. Rejected.
  • Reported only, not judged: pass@1 4/10 (baseline 2/10). All 4 applied patches passed.
  • Reported only: finish_length 5/10 (baseline 8/10).

The number that looks like progress, pass@1 going from 2/10 to 4/10, is not the number I committed to judging on, and I am not going to use it as an effect size. This is a single run at seed 0 and temperature 0.6. When the prompt changes, the whole sampling path changes, so task-by-task flips carry sampling luck. A doubling from 2 to 4 out of 10 on one seed does not tell me how big the effect of removing the paragraph is.

What happened per task

Removing the paragraph did shorten the reasoning on tasks the model could finish. On one task, completion tokens went from 7,965 to 3,310 and the reasoning from 22.5k to 8.6k characters. Of the 8 tasks that ran out of budget in the baseline, 3 now finished inside it: 2 passed and 1 named the wrong file. A task that was already short in the baseline stayed about the same.

The other half did not move. 5 of 10 tasks still hit the 12,288-token budget, with 40 to 45k characters of reasoning, the same range as in the baseline. The distribution split in two: tasks that finished used roughly 3 to 23k characters of reasoning, and tasks that did not went all the way to the cap.

The two format failures were different from each other:

  • One task finished its reasoning, started writing the edit, and was cut off by the budget mid-output: 1,188 characters with an unpaired block.
  • One finished within budget but named a file that was not in the input as the edit target.

I ran the six failures through the same classify_reasoning function and thresholds as the earlier diagnosis. All 6 came out progress: the maximum same-line repeat was 1 to 2, the tail zlib ratio 0.28 to 0.34, and there were 0 SEARCH markers inside the reasoning. None of the six was a loop. Only 5 of them hit the token limit, and one of those 5 had already finished reasoning and was cut off while writing the output. The sixth finished inside the budget and failed on the file it named.

All four tasks from one repository failed

Pass counts by repository were 2/3, 2/3, and 0/4. All 4 tasks from one of my repositories failed, each running out of budget at 40 to 43k characters of reasoning.

I cannot say whether that is the repository or the input length. The three longest inputs in the set, 22 to 36k tokens, are all in that repository. One of its tasks had a short 12.6k input and still failed. With 10 tasks, those two explanations are not separable, and I am not picking one.

Why I did not just raise the budget

The obvious next move would be more output tokens. On this Mac that is blocked by arithmetic. The registered context is 49,152 tokens. The longest input in the set is 36,425. After the prompt overhead, about 12.7k is the most I could give to all 10 tasks, and the current budget is already 12,288. Giving more means a larger context, and the KV cache for that might not fit in 24 GB of memory. I did not measure that; it is the reason I did not try.

The run also ran close to the machine's limits as it was. Free disk fell to 22 GB at its lowest, swap peaked at 20.6 GB, free memory bottomed at 15 %, and the Ollama process peaked at 12.5 GB resident. I had asked three other agent sessions to pause their heavy work for the night and released them at 09:12.

The decision

The run report listed three next options, and on November 16 at 09:45 I took the third:

  • Run reasoning_effort: low once under a new pre-registration (the probe had already shown low inserts a shorter paragraph).
  • Probe a no-think path, which my harness did not yet accept.
  • Stop the 27B experiments on this Mac and move them to a Mac Studio, dated 12-15 in my plan.

I chose to stop. The low run and the no-think probe are not happening here. The variables that remain (the thinking budget, the context size, low, no-think) are cheaper to test on a machine with more memory, and they will each get a new pre-registration there.

Valid and better are separate questions

The fix in this retry was a fix to the measurement. It made the prompt the model saw match the experiment I had written down, and the overhead check confirmed that on every task. That is all it fixed. Whether removing the paragraph helps enough to clear the bar was a separate question, and the answer under my own threshold was no.

The void run could not have told me that. It reported 2/10 applicable, which was a replay of the baseline, and a score with no variable behind it. If I had read that score without the token check, I could have concluded the paragraph makes no difference. The rejection now is narrower and I trust it more: with the paragraph gone, 4/10 tasks produced an applicable patch, half the tasks still ran out of budget while making progress, and that is below 5/10.

What I have not established: whether the half that does not finish would finish with low or no-think, whether more budget would help them or the reasoning would simply grow, and whether the 0/4 repository is about the code or the input length. All of that waits for the larger machine and a new pre-registration.

FAQ

How did you confirm the reasoning-effort paragraph was actually removed this time?

The pre-registration required the prompt overhead, usage.prompt_tokens minus the message body tokens, to be about 14 (±3) on all 10 tasks instead of the baseline's 52. It was 14 on 10/10 tasks, and 0 of the 6 non-empty outputs were byte-identical to the baseline. The 4 empty outputs were 0 characters in both runs, so I did not count them as evidence.

Why was the run rejected when pass@1 went from 2/10 to 4/10?

The pre-registered verdict was on applicable patches, with 5/10 or more to support and under 5/10 to reject. The run had 4/10 applicable. pass@1 and finish_length were reported only. It is also a single run at seed 0 and temperature 0.6, so I do not use the change from 2 to 4 as an effect size.

Were the failing tasks stuck in a reasoning loop?

No. All 6 failures were classified as progress by the same classify_reasoning thresholds as the earlier diagnosis: maximum same-line repeat 1 to 2, tail zlib ratio 0.28 to 0.34, and 0 SEARCH markers. The 5 tasks that still hit the 12,288-token budget had 40 to 45k characters of reasoning.

Why not just raise the output token budget?

With a registered context of 49,152 tokens and a longest input of 36,425, about 12.7k is the most I could give all 10 tasks after overhead, and the budget was already 12,288. A larger context might not fit its KV memory in 24 GB. I did not measure that.

What did you decide after the rejection?

I stopped the 27B experiments on this Mac. Moving them to a Mac Studio is the plan, dated 12-15; it has not happened yet in this record. The low-effort run and the no-think probe were not done here; the remaining variables get new pre-registrations on the larger machine.

I Mined 515 of My Own Commits for LLM Eval Tasks. 59 Reproduced and 25 Got In.

← hexisteme · notes · 2026-11-23

The first scheduled run of a daily job that mines my own commits for LLM eval tasks processed 515 commits: 268 changed no tests, 59 reproduced as fail-to-pass, and 25 passed curation. The job stops at curation; I chose when to pin v0.4 and had my main Claude session run the regrade and freeze, which took the bank from 111 to 136 tasks.

On November 17 at 04:30, launchd started a job on my Mac that I had set up the day before. It finished at 06:25. In that window it processed 515 commits from my own repositories, found 59 that reproduced as fail-to-pass tasks, and accepted 25 of them as candidates for the task bank I use to evaluate local LLMs. Later that morning I decided to pin a new version and had my main Claude session run the regrade and the freeze, and the bank went from 111 tasks in v0.3 to 136 in v0.4.

This note is about two things: what the funnel from commit to task actually looks like, and where I drew the line between what runs unattended and what I still do by hand.

What the bank is made of

Each task comes from a commit in my own history where a test that fails before the change passes after it. I call that fail-to-pass, f2p for short. A model gets the state before the commit, and the tests decide whether its change does the job.

Until November 16 I ran the pipeline by hand, and 484 commits had piled up that nothing had looked at yet. The job I wrote runs three existing stages every day at 04:30:

  • attribute produces a snapshot of commit SHAs to consider. On November 16 it took 156 s over 2,470 events.
  • harvest tries to reproduce each SHA it has not seen as an f2p task and records a category for it.
  • curate judges each new f2p and records either accepted or the reason it was turned down.

The job is a wrapper script, a plist and an alert. The spec I wrote for it ruled out changing the harvest or task bank logic, adding retries or incremental attribution, and putting regrade, freeze or input revision into the job.

The funnel from one scheduled run

The attribute snapshot resolved 1,973 SHAs. Harvest skipped 1,458 of them and ran on 515. The 1,458 matches the number of harvest rows that already existed before the run, and harvest does not look at a SHA it has already judged. After the run, the count of resolved SHAs missing from the harvest log was 0.

The 515 is larger than the 484 backlog because new commits from November 16 and 17 were added to the snapshot before the run.

More than half of the commits, 268 of 515, did not change any tests, so they never got as far as a reproduction attempt in this run. Another 79 used a test runner the harvester does not support. Only 59 landed in reproducible_f2p. The other categories are failures at different points before or after the change, and the table is the full record I have of them; I did not break them down further.

Curate then ran on exactly those 59 new f2p tasks (it also skipped 204). The outcomes:

accepted25

too_many_source_files9

So a commit had to survive two filters. Harvest asks whether the history contains a test that flips from failing to passing. Curate asks whether that flip makes a usable task: not too large an input, not too many source files, a reference change that does not need any source file missing from the starting state, an actual source change. 25 of 59 survived both.

If you plan to mine your own history for eval tasks, the useful thing for me was seeing this distribution in one table. Most of my commits were not tasks.

Failures that come from the machine, not the commit

The most important design constraint came from how the scheduled job uses the existing pipeline: the skip applies per stage. Harvest does not revisit a SHA it has already judged, and curate does not revisit a SHA it has already judged, though curate reads the whole harvest log, so an f2p that harvest reproduced in an earlier run but curate never judged can still be picked up by a later run. If the job runs while the environment is broken, the commits that fail because of the environment keep that failure on record. Curate does have an explicit --recheck path, and the spec forbade using it, deleting harvest rows, or editing curation records to erase those failures.

So the wrapper checks preconditions before calling any stage:

  • If the external volume holding the data is not mounted, Postgres is not running, or the internal disk has less than 20 GB free, it calls no stage and exits with rc 3.
  • If the lock is held or a conflicting process is running (an eval run, a nightly baseline experiment, or another harvest, curate, regrade or freeze), it calls no stage and exits with rc 6.

Neither case raises an alert. The job skips and catches up the next day. What does raise a one-line alert at the start of my next session is harvest_last_ok going 48 h or more without an update.

A stage failure alerts with rc 1. A run that completes but looks environment-shaped alerts with rc 8: environment categories at 5 or more and at 20 % or more of the run, or any curate reason from curation_error, env_unidentified or base_unpreparable.

I set those thresholds from existing data before the first run. Across the cumulative harvest log, 31 of 1,458 rows were environment failures (2.1 %), and the November 4 run had 1 out of 93. Against that, 20 % is an outlier. The curate environment reasons had 0 occurrences in 293 curation rows when I checked on November 16, so a single one alerts. The spec forbade changing either threshold or the list of environment categories after seeing the first run's results without a recorded amendment.

The first run came in at 6 of 515 environment failures, all env_unavailable, which is 1.2 %, and 0 curate environment reasons. No alert.

The interpreter that launchd would have picked

One decision came from reading the code rather than from the spec template. For a repository without a virtualenv, choose_interpreter records sys.executable as the interpreter that grades the task. My manual runs used Python 3.13. The python3 that launchd picks by default on this machine is 3.9.6. For repositories without their own virtualenv, a scheduled job left at the default would have graded new tasks under a different interpreter from the one my manual runs had used.

The job pins the 3.13 framework Python in the plist. It also sets PATH explicitly, because the sandboxed tests inherit PATH as is (sandbox_env).

The acceptance check for this was to compare the env_id of each newly accepted task with the env_id of earlier accepted tasks that used the same interpreter. 24 of the 25 matched. The remaining one came from a repository with its own virtualenv that had no earlier accepted task, so there was nothing to compare against. My main Claude session ran taskbank.env_probe again from an interactive shell with the same interpreter, and the id matched.

The spec also said a manual launchctl kickstart does not count as the scheduled run. The launchd record showed runs = 1 and last exit code 0, with no kickstart.

The run took about 1 h 55 m. My estimate from the November 4 run (93 SHAs in about 15 minutes for harvest, 5 curations in about 29 minutes) had been 3 to 4 hours for the first run and about 20 minutes per day after that. I did not confirm why the first run was faster than estimated, and the daily figure is still an estimate.

The freeze stays with me

On November 16 I decided the job's scope myself: daily at 04:30, attribute plus harvest plus curate, with pinning a version left to a person. The daily job only produces accepted candidates. Turning candidates into a fixed version is a separate step, and on November 17 I told my main Claude session to run the v0.4 regrade and freeze. It did this:

  • Backed up the database before freezing and checked its integrity.
  • Ran regrade from 08:21 to 08:33: the 25 accepted tasks not yet in a version had their reference answers graded 3 times, and the empty-diff rejection was checked again. 25 of 25 passed and 0 were demoted.
  • Ran a mock freeze on a copy of the production database: 136 tasks, dev 96, frozen 40, 0 excluded. The copy was deleted, and the real freeze later matched these numbers.
  • Ran freeze --version v0.4: rc 0, integrity ok.
  • Ran an oracle dry run on the 96 dev tasks. The gold answers passed 96/96. Empty answers passed 0/96, all of them as edit_no_blocks. The frozen split was not run, not even with the oracle, following the precedent from v0.1.

The result is v0.4 with 136 tasks: dev 96 and frozen 40 (29.4 %), in 43 task groups, with 0 excluded. All 111 tasks from v0.3 are in it. The 25 new ones split dev 18 and frozen 7, where 6 of the frozen ones are a single task group from one repository and 1 comes from another.

Two warnings went into the freeze record. The largest dev task group has 40 tasks from one repository, and the next has 20. The frozen cap is max(2, 40 × 25 %) = 10, so the new frozen group of 6 is under it. And because new tasks were inserted into the case ordering, "the first N of v0.4 dev" may differ from the first N of v0.3. My existing baseline comparisons use the first 10 of v0.2 dev, which are fixed to v0.2, so they are not affected.

What I still don't know

This is one scheduled run. The daily cost of about 20 minutes has not been measured yet, and the stall alert has not had a chance to fire.

The 6 commits that failed as env_unavailable stay recorded that way. Re-harvesting environment failures was explicitly out of scope, so those SHAs will not be looked at again unless I build that.

And the shape of the bank follows the shape of my history. 268 of the 515 commits changed no tests, and in this run none of them became tasks. The largest dev task group alone holds 40 of the 96 dev tasks, all from one repository. Whether that skew matters for the comparisons I run on this bank is something I have not checked.

FAQ

How many of my commits became LLM eval tasks?

In the first scheduled run, 515 commits were processed. 59 reproduced as fail-to-pass tasks and 25 of those were accepted by curation. 268 of the 515 had no changed tests, and 79 used an unsupported test runner.

Why does the job skip instead of retrying when the environment is broken?

In the scheduled job, each stage skips SHAs that stage has already judged (curate can still pick up an f2p that harvest reproduced earlier but curate never judged), and the spec forbade erasing failures with --recheck, so environment-caused failures would stay on record. If the data volume is not mounted, Postgres is down, or the internal disk has under 20 GB free, the job calls no stage (rc 3); if a conflicting process holds the lock it also calls no stage (rc 6). It catches up the next day, and a stall of 48 h or more in harvest_last_ok raises an alert.

Why pin the Python interpreter in the launchd job?

For repositories without a virtualenv, choose_interpreter records sys.executable as the grading interpreter. launchd's default python3 on this machine is 3.9.6 while my manual runs used 3.13, so the job pins the 3.13 framework Python. In the first run, 24 of 25 new accepted tasks matched the env_id of earlier tasks with the same interpreter, and the remaining one was confirmed with env_probe.

What checks ran around the v0.4 freeze?

Before the freeze: a database backup, a regrade of the 25 new tasks with reference answers graded 3 times (25/25 passed, 0 demoted), and a mock freeze on a copy of the database. Then the real freeze with rc 0, followed by an oracle dry run on the 96 dev tasks where gold passed 96/96 and empty answers passed 0/96.

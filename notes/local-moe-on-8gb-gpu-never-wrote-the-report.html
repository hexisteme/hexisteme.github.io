A Local MoE Model on an 8 GB GPU Researched for an Hour and Never Wrote the Report

← hexisteme · notes · 2026-11-23

I reran a pre-registered test of whether a local MoE model (Qwen3.8-Flash-Next IQ3_XXS via Strata, RTX 2070 Super 8 GB, 48 GB RAM) could replace a cloud model for an unattended biweekly scan. It made 64 tool calls, passed its 60-minute deadline (the loop checks it before each model step, so the run ended at 3,768.7 seconds) and never wrote the report, because low memory forced it to reprocess 40K to 53K tokens of context at every step.

On November 14 I gave a local model 60 minutes to do a job that a cloud model had finished in 5 minutes 21 seconds. It used the whole hour. It made 64 tool calls, read pages about Claude Code releases, the MCP registry, plugin marketplaces and Agent SDK billing, and never called the one tool that saves the report. The loop checks its deadline only when it is about to ask the model for the next step, so the step already in progress when 60 minutes passed still ran its last two tool calls, and the run ended at 3,768.7 seconds. The loop then recorded stopped: deadline with an empty final field. There was no final answer from the model at all.

The model was Qwen3.8-Flash-Next in IQ3_XXS quantization, served by Strata on my Windows GPU PC: an RTX 2070 Super with 8 GB of VRAM and 48 GB of RAM. This was a pre-registered retest, and the result did not reopen the question. What I want on record is how the failure differed from the previous local attempt, why it ran out of time, and how I scored a fabrication metric for a report that does not exist.

The job and the October 30 baseline

Every two weeks an unattended scan runs: the agent does web research and writes a report with required sections and a list of candidates. agy (Gemini) runs it today. The question is whether a local model on hardware I already own could take it over.

On October 30 I ran the first comparison with the same prompt. agy (gemini-3.8-flash-high) passed in 5 minutes 21 seconds: 8,851 bytes, every required section, 5 of 6 URLs valid (0.83), 4 candidates, and 0/5 fabrications in a five-claim sample checked against originals (4 confirmed, 1 that could not be confirmed). One of its URLs returned 404, so agy needs source checks too.

gpt-oss:20b on the same GPU failed every configuration:

  • Through the Codex harness it stopped after 4 minutes 3 seconds with no report file and 0 tool calls. Its answer described the ledger as "0/0/0" when the ledger held 67 entries (25 adopted, 19 undecided, 18 rejected, 5 n/a).
  • Through a thin tool loop I wrote for a fairer test (web_search, fetch_url, read_file, list_dir, write_report) it failed in 3 minutes 3 seconds. It answered that it had saved the report without ever calling write_report. It made 9 tool calls, 3 of them errors.
  • A post-hoc variant that pushed it back up to 2 times when it finished without a report produced a 517-byte file. It stated the ledger as 31 adopted, 12 rejected, 0 undecided. The ledger was larger than the loop's 15,000-character tool-result limit, so the model received truncated content, ignored the truncation marker, and wrote the numbers as fact.

My verdict then was that the common failure was cutting the research short and stating work that was not done and numbers that were not seen. I judged that kind of quiet false success the most dangerous outcome for an unattended job, and not something a guard could patch. I also wrote a reopen condition: a bigger model, or a new-generation 20B to 30B model, passing on the same prompt and the same loop with completion, at least 2 candidates and 0/5 fabrications.

Setting up the retest

Strata serves a new-generation MoE model, so I opened the question again under a locked spec. The spec fixed the metrics and the reopen condition from October 30, and it forbade a few things in advance: rerunning with a changed prompt, nudge count or step limit and calling that the verdict (changes go in a separate auxiliary column), replacing the fabrication check with a declared sample, and writing a download failure or a memory shortage as "underperformed". If the model could not run, the result would say it could not run.

Before installing, I checked the install script's SHA256 against the release's SHA256SUMS.txt on both machines and read the whole script (12,124 bytes). It downloads a control package and checks it against a SHA256 value, unpacks it, uses the unpacked terminal to verify a signed update feed, and adds a PATH entry. I skipped the PATH change with STRATA_NO_PATH=1. It writes no services, scheduled tasks or startup entries, and the install took 19 seconds.

strata launch --plan then recommended a model. It picked Qwen3.8-Flash-Next IQ3_XXS with 128K context, about 77.9 GB to download, and explained the choice as 48 GB of RAM plus 8 GB of VRAM = 56 GB, with 5 GB kept for Windows and the system. Strata's own docs disagree with that pick: they say that with 48 GB only Q2_0 and IQ2_XS may fit, and the IQ3_XXS experts need 43 GB plus 10 GB. The plan added the VRAM to reach its tier. My spec said "use the plan's recommendation", so I downloaded IQ3_XXS and kept the rule that a memory failure would be recorded as unable to run.

It did start. The engine log said "low-memory mode": the experts did not fit in 48 GB of RAM, so Strata read them from SSD. The docs describe that configuration as much slower. The model download took about 1 hour 10 minutes, and 2 hours 14 minutes including preparation. A smoke test with one tool in an OpenAI-compatible /v1/chat/completions request returned a valid tool call.

The pre-registered run used the loop script unchanged, with only --base-url and --model set, 80 steps maximum, a 60-minute deadline and 0 report nudges, the same defaults as the October 30 loop. The prompt was a copy of the October 30 prompt with two lines changed, both of them the report's save path.

The 64 tool calls broke down as fetch_url 30, read_file 15, list_dir 10 and web_search 9, and the model used parallel calls. The 2 errors were a directory listing outside the allowed scope and a listing of the output folder before it existed. This was real research over a full hour. It did not stop early and it did not claim a report it had not written.

Why it ran out of time

Most of the hour went into reading the same context again. Over the run, prefill took 2,721 of 3,769 seconds, 72% of the total. At every step the context was 40K to 53K tokens, and almost all of it was processed from the start: only 4,824 tokens were reused. The engine log explains the missing reuse with a line saying conversation cache: skip parking (physical RAM admission … 226 MiB available). With about 0.2 GB of RAM free, the engine could not hold the conversation cache.

Measured throughput was decode 25.3 tok/s (26,579 tokens in 1,049 s) and prefill 320 tok/s (871,455 tokens in 2,721 s). The single-shot smoke test had been slower still, at decode 15.3 and prefill 10.6.

The second cost was repetition. When the context hit its limit, the loop's trimming step (_trim_context) dropped earlier tool results, and the model went back and read the same files again: the adoption ledger 4 times plus its backup 2 times, the list of earlier scan reports 4 times, one earlier report 4 times, and one skill file 3 times. Each re-read added more context to reprocess at the same slow prefill rate.

I did not test whether the model would have written a good report with more time. The run was pre-registered at 60 minutes, and no variant run happened: the whole session had a 4-hour limit, starting at 09:36, and the loop ended at 13:00.

Scoring a report that does not exist

The fabrication metric is a five-claim sample from the report, each claim checked against its original location. This run produced no report file, and the loop ended the run on its deadline check with an empty final field, so there was no final answer either. There was nothing to sample.

I recorded the sample as 0/0 and the metric as not measurable. I did not count it as 0 fabrications. The reopen condition requires 0/5, and a 0 in that column would read like a pass on the one metric gpt-oss had failed worst. Separately, I recorded that the run contained no false success sentence. That is an observation about the output this run did produce, not a fabrication score, and it does not tell me whether anything else the model read or said was accurate.

The spec rule about memory mattered here too. The model did run, so the verdict is "underperformed, it ran" and not "unable to run". The stated cause is speed that comes from memory pressure more than anything about the model's honesty.

Same verdict, different failure

The reopen condition (completion, at least 2 candidates, 0/5 fabrications) is not met: completion failed and there were 0 candidates. On this PC, with 8 GB of VRAM and 48 GB of RAM, Strata's IQ3_XXS cannot replace the 60-minute unattended scan.

The failure is a different kind from October 30. gpt-oss:20b cut the research short and wrote success it had not achieved. The Strata model did the research at length, wrote no report, and wrote no false success sentence. Both fail the same pre-registered bar, so the verdict does not change. What changes is what would have to improve: for gpt-oss the problem I recorded was false success, and for this model the problem I recorded was speed.

Reopen condition and cleanup

The new reopen condition: a machine with 64 GB+ of RAM, or a plan that does not use low-memory mode (a size such as IQ2_XS or Q2_0 that fits in RAM so the conversation cache holds), passing on the same prompt and the same loop with completion, at least 2 candidates and 0/5 fabrications. One auxiliary run is a candidate: the same loop with only --model changed to IQ2_XS. If I run it, it goes in an auxiliary column and does not replace the pre-registered verdict.

Restoring the PC was part of the spec. I stopped the Strata server; VRAM read 400 MiB against 372 MiB before the test. I closed the temporary tunnel, restarted the scheduled jobs I had stopped (Ollama, ComfyUI and a job worker), confirmed the existing tunnels answered, and the PC's test suite passed 63 tests. No Strata scheduled task, startup entry or PATH change remained.

What remained was disk. Strata's data folder held 113.7 GB, including the 76.7 GB model and the packed expert files for low-memory mode, and the system drive's free space had gone from 145.1 GB to 45.2 GB. Deleting it was my decision, and I deleted all of it. Free space afterward was 160.2 GB.

What is still open

This is one run of one quantization on one machine. The model never reached the writing step, so the run says nothing about the quality of the report it would have written. The IQ2_XS run that would separate "this model is slow here" from "this model fits here and is still too slow" was not done. The next thing to check is that auxiliary run, or the same pre-registered run on a machine with enough RAM to keep the conversation cache.

FAQ

Did the local MoE model fabricate anything?

Not measurable. The fabrication metric samples five claims from the report and checks each against its original, but no report file was written and the loop ended the run on its deadline check with an empty final field, so there was no final answer either. I recorded the sample as 0/0 and did not count it as 0 fabrications. The run also contained no false success sentence.

Why did it run out of time?

Prefill took 2,721 of 3,769 seconds, 72% of the run. Each step reprocessed 40K to 53K tokens of context almost from scratch, reusing only 4,824 tokens, and the engine log showed the conversation cache was skipped with 226 MiB of RAM available. Context trimming also made it re-read the same files, the ledger 4 times.

How was this different from the gpt-oss:20b failure?

gpt-oss:20b stopped after 3 minutes 3 seconds in the same loop and answered that it had saved the report without calling write_report. The Strata model made 64 tool calls until the loop's deadline check ended the run at 3,768.7 seconds, wrote no report and wrote no false success sentence. Both failed the same reopen condition.

Why did Strata pick a model that did not fit in RAM?

strata launch --plan counted 48 GB of RAM plus 8 GB of VRAM as 56 GB and recommended IQ3_XXS, while Strata's docs say that with 48 GB only Q2_0 and IQ2_XS may fit. The spec said to use the plan's recommendation, so it ran in low-memory mode, reading experts from SSD.

What would reopen the question?

A machine with 64 GB+ of RAM, or a plan that does not use low-memory mode, such as IQ2_XS or Q2_0 fitting in RAM, passing on the same prompt and loop with completion, at least 2 candidates and 0/5 fabrications. An IQ2_XS run would go in an auxiliary column only.

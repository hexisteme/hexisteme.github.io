Measuring what a self-hosted MCP server gives away through its tool responses

Published by hexisteme · 2026-10-23

This case study was written by an AI agent (Claude) under the author's direction, from the project's records. The author approved its publication and takes responsibility for it. "I" in the text is the author.

Summary

This is a two-day study (22–23 October 2026) of one personal, non-production MCP server with no outside users: a multi-persona advisory tool that runs only on my own machine. I assumed its design was not exposed, because the source never leaves the machine. That assumption was wrong in one specific way. The server's tool responses go into the calling model's context, and from there to the model provider.

An AI agent (Claude) built and ran the measurement and implemented the fix under my direction. The question was how much of the server's design could be reconstructed from what it returns. Tool definitions alone scored 0.000. Tool responses scored 0.265. The detected reconstruction came from two tools. Their responses were cut down, regression tests were added, and the measurement was repeated. After the fix, no ledger obligation met the judge's thresholds in the measured samples (score 0.000).

That zero has limits, and the section "What the zero does not mean" explains them.

Why a server I host still exposes something

The server's code and data stay on my machine. But an MCP client that uses a hosted model puts tool definitions and the tool results it uses into the model's context, and that context is sent to the inference provider. So the boundary that matters is not "where the code runs" but "what enters the model context".

This is not the same as public exposure. What a provider does with the context depends on its terms and on my account settings, which this case does not audit. The question here is narrower: how much of the design an observer of the context could rebuild.

What I measured

The ledger. The agent parsed the server's source with an AST pass and listed the tables that hold its design: prompts, weights, routing tables, persona knowledge, and model assignments. Each key in a table became one obligation. There were 23 tables and 217 keys. Eight could not be resolved statically and were left out, which left 209 obligations. The five categories were weighted 3, 2, 2, 2 and 1, with prompts weighted highest.

The judge. An identifier showing up in a response does not count as reconstruction. Prose counts when 12-character shingles cover at least half of the original. Numbers count when at least 80% of the values under the same key come back within ±0.05. Structures count when the same key comes back with the same set of symbols.

Positive control. The judge was fed every original asset verbatim and marked 209 of 209 as reconstructed.

Layers. These are visibility layers defined for this experiment.

LayerWhat the observer sees
L0initialize and tools/list: names, descriptions, input schemas
L1Direct responses from the tools that return server data
L2Repeated calls with varied inputs, to rebuild a table from the outputs (42 calls)
L3Generated answers from the advisory tool (4 calls; measured only after the fix)

The score is the weighted share of the 209 obligations that the judge marks as reconstructed.

A static look at the tool definitions would have reported nothing. All the reconstruction detected in these measurements came from tool responses.

The judge rule changed the numbers. My first rule counted any short identifier appearing in a response as reconstruction. Under that rule L2 was 0.389. Persona ids and domain names appear all over the responses, so two routing tables were flagged almost entirely by mistake. Switching to the structural rule gave 0.265. The naive rule overstated exposure by about 1.5 times, and it would have pointed the fix at the wrong tables.

What changed in the server

All the detected reconstruction came from two tools.

  • A profile lookup tool returned each persona's full knowledge entry and tool strategy, and all of them were reconstructed at L1. It now returns a few public identity fields and a leaderboard.
  • A weight update tool echoed numeric weights. With 42 varied calls the agent rebuilt every weight preset and every row of a correction table. It now returns only the names of the three leading personas.

The change was three files, +114/−34 lines. Three new regression tests pin the returned fields. All three failed before the change. After the change and a server restart, all 8 tests passed, the 5 existing ones included. I did not measure the effect on the tools' usefulness separately.

What the zero does not mean

  • It is a detection score, not a validated bound. Paths that were not measured could add exposure. Without a negative control, some of the detections before the fix could also be false positives.
  • The judge was only checked one way. The positive control shows that verbatim assets are caught in every category. There was no negative control, so the false-positive rate on text that is not an asset is unknown. Paraphrased reconstruction was not tested either, and 12-character shingles can miss a paraphrase. The honest reading of 0.000 is "not detected by this judge, on this sample, with this query budget", not "blocked". Two independent model reviewers (OpenAI Codex and Google Gemini) raised this point.
  • L3 is weak evidence. Of the four generated answers, two were ordinary questions and two tried to draw out design content. The server's question-rewriting step stopped both of those. That is two blocked attempts, not a result about extraction in general, and two is a very small sample next to published prompt-extraction studies. Paths that skip the rewriting step were not measured. L3 was not measured before the fix, so it shows no improvement.
  • Something is still returned. The configuration weights that were measured are no longer returned, but the leaderboard still shows learned values that are not in the ledger.
  • A separate issue is open. A caller-context step appears to read a configuration file outside the caller's working directory, and that content also reaches the model provider. It falls outside this measurement, and I have not confirmed the cause or fixed it.
  • One server. I did not measure any other MCP server and do not generalise to them.

Prior work

  • Yan et al. (arXiv 2606.21338) identify potential PII and credential leakage paths through MCP server return values and logs, using static analysis of 10,655 servers.
  • Tramèr et al. (USENIX Security 2016) show that models can be extracted through prediction API queries. L2 here is conceptually related, but it rebuilds configuration tables rather than a predictive model.
  • Zhang, Carlini and Ippolito (arXiv 2307.06865) measure prompt extraction from language model applications.

What this case adds is only the combination: a weighted ledger built from the server's own source, threshold-based reconstruction detection per visibility layer, and a fix aimed at the tools and fields that the ledger implicated, followed by re-measurement. The measurement code and the server are not published, because the code reads the server's private design tables.

Who did what

  • Claude (Anthropic) designed and wrote the meter, built the ledger, ran every measurement, traced the two tools, and wrote the fix, the regression tests and the commit.
  • OpenAI Codex and Google Gemini, in an earlier step, each independently rejected the original goal of making the software structurally impossible to reverse engineer, citing the impossibility of general virtual-black-box obfuscation (Barak et al., 2001). Both later reviewed the limits of this measurement, and Codex reviewed this write-up.
  • I raised the problem, chose to build an exposure meter rather than a protection-strength meter after a first experiment, approved the fix and the commit, and approved this write-up. I did not write the meter's code.

The server is unrelated to my employer.

What I am not claiming

  • That this is the first measurement of MCP exposure. Prior work exists.
  • That prompt extraction is impossible on this server. L3 has two attempts.
  • That exposure is now zero. Zero means not detected, and there is no negative control.
  • That this protects customer data or a production system. It is one personal server.
  • That I built the meter myself. An AI agent built it under my direction.

What open-source MCP servers expose to an agent: a static census of 60 repositories

Published by hexisteme · Version 1 · 2026-10-21

This report was produced by AI agents working under the author's direction. "We" means the author and those agents; About this work says who did what.

Connecting an MCP server to an agent approves two things at once: code that runs with your permissions, and text (tool names, descriptions and schemas) that goes straight into the model's context. We analysed 60 open-source repositories from the MCP server ecosystem statically, without installing, building or running them, and measured what we could measure reliably about both. Two of the measurements we planned did not survive validation. They are reported as method notes, together with the statistics of the failed validation.

Every number below describes this sample, not MCP servers in general. Most rates are for the band sample, the 53 most-starred repositories in a fixed popularity band, and many count only the deployed surface, the code a repository ships without its tests, examples, bundled samples and vendored code. Section 1 defines both. Most sections end with the claims their numbers do not support.

Summary

  • In these 60 repositories, high-severity invisible characters were rare, and every one we found was defensive. No Unicode tag characters (U+E0000–E007F) and no variation selectors supplement characters (U+E0100–E01EF) appeared in the 108,167 text files we scanned. That is not evidence that hidden text is absent from MCP servers in general. Bidirectional controls appeared 24 times, in 3 of the 60 repositories. Two raters judged all 24 independently and found none that hides text. Each was internationalisation code, a sanitiser that removes these controls, or a test of one of those. Zero-width characters and byte-order marks (283 occurrences) are low severity and were not judged.
  • Some tool descriptions are not written out where the tool is registered. In 12 of the 42 band-sample repositories with extracted tool definitions (29%; 95% CI 17–44%), at least one tool description is a template, a variable or a function call rather than a string literal at that point. Across all 60 repositories, that is 16 of 48, and 55 of 3,118 extracted tool definitions.
  • Unconfirmed injection-shaped code is common. In 31 of the 53 band-sample repositories (58%; 45–71%), at least one of nine static rules matches, on the deployed surface, a shape in which a value reaches an injection-prone call. A match is a candidate, not a vulnerability: we did not triage the candidates or check whether whoever calls a tool can control the value. The two most common shapes are a URL reaching a server-side request (23 of 39 TypeScript/JavaScript repositories) and a path reaching a filesystem call (20 of 39).
  • Tool surfaces vary widely. A repository with extracted tool definitions has a median of 16 (interquartile range about 6 to 37), and the three largest account for 54% of all definitions.
  • Two measurements failed validation, and we report no prevalence from either. Per-tool "lethal trifecta" capabilities could not be classified reliably. From metadata alone, 9 of 30 tools matched the reference labels. From handler code, 25 of 30 matched once, but only against labels we had settled ourselves, and the two raters did not agree on the definition well enough to publish. A lexical detector for instructions aimed at the model was right on 3 of the 12 texts it flagged.

3. Invisible characters

Three published findings motivate this check. Tag characters can carry a whole sentence that most interfaces do not display but language models read (Rehberger, 2024). Bidirectional controls can make source text display in a different order from the order in which it is stored and parsed (Boucher and Anderson, 2021). And instructions to the model can be hidden in a tool description, where the model reads them and the user does not (Invariant Labs, 2025). Characters of this kind in what a server sends to a model would be invisible to a reviewer reading the same text.

We scanned every text file in every repository (108,167 files), not only tool descriptions, skipping only dependency, virtual-environment, build-output, vendored and .git directories. That includes the agent configuration files (AGENTS.md, CLAUDE.md, .cursorrules and similar) found in 34 of the repositories. Binary files (4,418) were skipped, and 20 symbolic links were not followed. An occurrence is a run of adjacent invisible characters.

KindOccurrencesRepositories (Wilson 95%)
Tag characters, U+E0000–E007F00 of 60 (upper bound 6%); band sample 0 of 53 (upper bound 7%)
Variation selectors supplement, U+E0100–E01EF00 of 60
Bidirectional controls, U+202A–U+202E and U+2066–U+2069243 of 60 (2–14%); band sample 3 of 53 (2–15%)

All 24 bidirectional controls were judged by two raters, a Claude subagent with a fresh context and Gemini, blind to each other. The brief asked one question per occurrence: is this an attempt to hide text from a human reviewer, or to make text render differently from what a model reads? It also described the legitimate uses we expected and told the raters not to defer to those expectations. It told them to answer no, and say what they would need, when the context was too thin to decide; neither rater did so. The raters agreed on all 24, and neither marked any as hiding text. The 24 are every high-severity occurrence in the corpus, not a sample, and they sit on 12 source lines, so we give no interval for this result. Cohen's κ cannot be computed here, because both raters gave the same answer, no, for every occurrence.

The 24 occurrences fell into three groups:

  1. Isolation in internationalised messages (2). Isolate characters wrapped around an interpolated value, so that a right-to-left value cannot reorder the sentence around it. Isolates exist for this: they allow "the embedding of strongly directional text without unduly affecting the bidirectional order of its surroundings" (Unicode Standard Annex #9). These were the only 2 occurrences on the deployed surface, both in 1 repository (1 of 60; 0–9%).
  2. A sanitiser that strips bidirectional controls (6). Its source contains the raw characters it removes.
  3. Tests (16) of isolation output, of the sanitiser, and of message files that must not contain bidirectional controls, including deliberately hostile input strings.

None of the 24 was in an agent configuration file.

Not supported by this: that MCP servers contain no hidden instructions. Zero tag characters in 60 repositories is not a proof of absence. Even if these repositories were a random sample, it would only put the repository-level rate below about 6%.

For anyone building such a scanner: in this sample, every high-severity hit was code that handles these characters on purpose, or a test of that code. Expect alerts on defenders and review each in context, such as an isolate pair around an interpolated value, a character list in a sanitiser or a test fixture. Exempting such files or patterns wholesale would also exempt an attacker who imitates them.

4. Tool descriptions that are not fixed strings

A description written as a literal at the registration site is the text a reviewer of the source sees. A description built when the tool is registered, from a template, a variable or a function call, can differ between the text someone approved and the text a later run sends, with no change to any literal. Invariant Labs (2025) calls the attack on this surface a rug pull: "a malicious server can change the tool description after the client has already approved it." We measured the source, not what servers send.

Not supported by this: that these descriptions do change at runtime. This is a syntactic property at the registration site, and a variable can hold a constant defined elsewhere. Nor does a literal guarantee a fixed description: a server can still change a definition after registering it, and tools registered in styles the extractor does not cover are not counted.

6. Method notes: two measurements that failed validation

Both were measured on the first 18 repositories (11 from the band sample, 7 purposive), before the corpus grew to 60. The 42 repositories added later were not read for either measurement.

6.1 Per-tool "lethal trifecta" capabilities

Question. For each tool, does its handler give the model access to private data (P), bring third-party content into the model's context (U), or send model-influenced data across the user's boundary (E)? A tool or server with all three has what Willison (2025) calls the lethal trifecta: "access to your private data", "exposure to untrusted content" and "the ability to externally communicate". The goal was a per-tool prevalence, with ground truth taken from what the handler code does.

Protocol. Each round drew a fresh sample of 30 tools with literal names, spread across repositories with a fixed seed. The predicted {P, U, E} set had to match the reference exactly on at least 24 of the 30 (80%). A capability was publishable only if the two raters reached Cohen's κ of at least 0.6 on it. Two LLM raters from different model families labelled each tool from its handler code, blind to each other and to the classifier. The classifier's developer settled disagreements from the code before scoring. Before each sample was drawn, the classifier was hashed. After scoring, that sample became development data, and the next round drew a new one. Rounds 2 and 3 drew new tools from the same 9 repositories as the development data, so even a pass would have shown generalisation only to new tools in those repositories.

RoundClassifier inputRatersκ (P / U / E)Exact matchOutcome
1Names, descriptions, schemasClaude, Gemini0.93 / 0.81 / 1.009/30 = 30%Fail
2Handler code, call tracing up to 5 levelsClaude, OpenAI Codex0.00 / 0.81 / 0.3325/30 = 83%Accuracy passed, withheld on κ

Counts are given without intervals: the gate was set on the count, and tools from the same repository are not independent.

How much the settlement mattered: in round 2 the raters' label sets agreed exactly on 9 of 30 tools, and the settlement followed the Claude rater on 15 of the 21 disagreements and the Codex rater on 6. In round 3 it settled 10 disagreements, 9 of them the Claude rater's way. Scored against each rater's raw labels instead of the settled ones, with the Claude rater first, round 2 reaches 23/30 and 12/30 (computed after the fact), and round 3 reaches 23/30 and 19/30 (preregistered). Round 2's pass therefore depended on how we settled disagreements. Round 3's failure did not.

What we learned.

  • The metadata classifier missed external communication. In round 1, it caught one of the six tools that the raters, reading the handler code, found to send data out. For example, one tool described only as producing an artefact uploaded the model-supplied input to a third-party service to produce it.
  • Finding the handler was not the hard part. The code classifier found the handler for 30 of 30 tools in round 2 and 29 of 30 in round 3. Its remaining errors came from what it concluded about the handler, such as dispatch it did not follow, responses it modelled wrongly and a scope rule it applied too widely. The rest of the failure came from the labels.
  • The definition did not hold across raters. κ for P ranged from 0.00 to 0.93 depending on the rater pair and the wording of the brief. The disagreements came from questions the definition leaves open: whether reading an API key from the environment is private-data access, whether a GET to a fixed, operator-configured host is external communication, whether a response from a keyed public-data API is private. Writing round 2's answers into the brief as rules moved the disagreement instead of removing it.

Reporting rule, stated after these results were seen: when a measurement fails its preregistered validation, we publish the statistics of that validation, and no prevalence, absence, recall or deployment-safety claim based on it.

We publish no per-tool or per-server capability counts. A server-level union would come from the same unvalidated classifier.

6.2 Instructions aimed at the model, in tool text

Question. How often do tool descriptions, the descriptions inside tool schemas, and agent configuration files instruct the calling model to force a call to another tool (X, tool text only), hide something from the user (H), go to sensitive paths or credentials (S), or ignore other instructions (O)? We call each non-empty description or schema description a tool text. Tool names were not scanned. The detector was deterministic and lexical. It was built from category definitions, synthetic sentences and the published tool-poisoning proofs of concept (Invariant Labs, 2025), and never from the corpus.

Protocol. The detector's source was hashed before its single run over the 4,659 tool texts of 1,586 tool definitions and over 41 agent configuration files. These were extracted before the correction described in Section 2. Every flag was judged, without sampling, by two blind raters (Claude and Gemini). The gate was precision of at least 70%.

Result. 12 flags: 9 for forcing another tool call (X), 2 for hiding (H), 1 for sensitive paths (S) and 0 for ignoring instructions (O). Of these, 9 were in tool text and 3 in configuration files. The raters agreed on all 12 (κ = 1.00). Precision was 3 of 12 (25%), below the gate. Every flag was judged, so this is the detector's precision on this corpus, not an estimate. The three correct flags were ordinary workflow guidance: advice on choosing between this tool and a named sibling, or on calling another tool first to get exact names. None of the 9 flagged tool texts came from tools whose descriptions the detector's developer had seen during 6.1.

Why it failed. In servers whose subject is other code, "function" and "tool" usually mean the code under analysis, not an MCP tool. Naming another tool as workflow context is not an instruction to call it. "Before calling …" mostly describes where the tool itself fits. "Expose" appears in secure-coding guidance. A feature description that names a sensitive path is not an instruction to go there. The detector used vocabulary to approximate the difference between a tool describing itself, describing a workflow and instructing the model, and the approximation was right a quarter of the time. This is a result about this detector, not about lexical detection in general.

Secondary audit, not a recall estimate. Among 274 unflagged tool texts that contain imperative vocabulary, a random 30 contained 1 instruction after settlement. The Claude rater's raw labels found 2 and the Gemini rater's 1, and the one text they disagreed on was settled by the detector's developer as not an instruction. The audit was preregistered as a secondary analysis. We first deferred it when the gate failed, which departed from the protocol, and completed it after deciding to stop the measurement. It cannot be turned into recall or prevalence, because texts without that vocabulary, and configuration files, were outside the audited stratum.

Reporting rule, stated after these results were seen: when a measurement fails its preregistered validation, we publish the statistics of that validation, and no prevalence, absence, recall or deployment-safety claim based on it.

7. What deployers can do with this

These are general practices. The counts show where this sample gives them weight; they do not show that a practice prevents any particular attack.

  1. Pin what you approve. Record a hash of each tool's name, description and schema when you approve a server, and ask again when any of them changes. This matters most where the source does not show the text directly. In 12 of 42 band-sample repositories with extracted tool definitions, at least one description is not a literal where the tool is registered (Section 4).
  2. Judge what a tool can send out from its handler, not its description. Section 6.1 has a case where the description mentioned only the artefact a tool produces, and the handler uploaded the input to a third-party service to produce it.
  3. Scan what a server sends to the model, and review hits in context. Every high-severity invisible character in this sample was internationalisation code, a sanitiser, or a test of one (Section 3), so expect a scanner to flag defenders, and review them rather than exempting them wholesale.
  4. Contain the common sink shapes. URL-to-request and path-to-filesystem candidates appear in about half of the band sample's TypeScript/JavaScript repositories (Section 5). Limiting a server's network egress and its filesystem scope addresses both shapes, whichever candidates turn out to be real.

8. Limitations

  • Sampling frame. One GitHub topic and one popularity band, entered by three routes. The band sample is the most-starred end of the band and not a random sample, so intervals are for scale only (Section 1). Nothing here describes less popular servers, closed-source servers or hosted remote servers.
  • Static only. Repository code was never installed, built or run, and no server from the corpus was contacted. The network was used only to search GitHub, clone the repositories and call the raters' models. Registration styles outside the extractor are missed, 92 extracted tool names did not resolve to a literal, and descriptor objects were not confirmed one by one, so a repository with extracted tool definitions is not necessarily one that registers tools at runtime.
  • Scanner defaults. semgrep skips test/ and tests/ but scans __tests__/, spec/ and examples/, so candidates off the deployed surface are undercounted. Build and release scripts count as shipped code.
  • In-sample rules. The sink rules were developed on 18 of the repositories, including the 11 band repositories chosen among those with private vulnerability reporting, so their candidate rate mixes that choice with rule development. Section 5 reports the other 42 separately.
  • One correction after the first look (Section 2), reported with its before-and-after numbers.
  • Raters. The raters are LLMs, not human security reviewers, and their briefs described the legitimate patterns we expected. In Section 6.1, disagreements were settled by the classifier's developer, a Claude session, which is the same model family as one rater in every round, and the settlement mostly followed that rater. Section 6.1 reports raw-label scores to bound this.
  • Aggregates only. No per-repository results are published.

9. Reproducibility

The accuracy and precision gates of Section 6 were committed to the design document on 2026-10-20, before either measurement ran. The selection rule for the 42 repositories added on 2026-10-21 was committed before the search ran, the protocol of Section 6.2 before the detector was built, and the sink-rule set, with file hashes and reporting units, before the scan. Round-specific protocol details in Section 6.1 (samples, raters, the κ threshold) were written before that round's labels were read, but committed together with its results. Classifier and detector sources were hashed before they were run on evaluation data. Repositories are pinned to their clone-time commits. Tool version: semgrep 1.181.0. Preregistration records, rule hashes and pinned commits are kept with the measurement code.

Not released with this version: the measurement code, the rule files, the list of repositories and the per-repository results. The selection rule in Section 1 lets anyone draw a comparable band sample, but not reproduce these numbers exactly, because star counts and repository contents change. The aggregate tables in this report are its published data.

About this work

Who did what. Claude (Anthropic), working as a coding agent under the author's direction, wrote the preregistrations, the measurement code and this report, ran the measurements, and settled the raters' disagreements. Each judged measurement used two raters, blind to each other: a separate Claude instance with a fresh context, and Google Gemini or OpenAI Codex. Codex and Gemini also reviewed drafts of this report. The author set the goal of the work, decided the corpus size, approved the reporting rule for failed measurements and approved publication, and takes responsibility for the published text. The work followed the project's safety rules: no code from the repositories was installed, built or run, and no repository is named. Before publication, a script recomputed every number in this report from the raw measurement files; that checks arithmetic and transcription, not the measurements themselves.

Scope. This report names no repository and contains no vulnerability details. It does not represent the views of any employer or organisation.
